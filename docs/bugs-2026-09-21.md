## Bug #1: `newsflash` 任务在窗口内只跑一次（interval 配置形同虚设）

### 现象
- `DEFAULT_TASKS` 里 `newsflash` 配置 `interval_seconds=60` + `window=intraday(09:26-10:00)`
- 意图：盘中每 60 秒重复拉快讯
- 实际：今天上午 09:26:02 成功后，**09:27 至 10:00 之间再也没有跑过**，整段窗口只跑 1 次（rows=20）
- worker.log 里没有任何 `ingest_task_skipped` / `newsflash` 在 09:27 之后的日志行

### 根因
**位置**：`backend/app/ingest/scheduler.py:333-335`

```python
for defn in self._select_tasks(window, moment):
    if await _state_status(repos, defn.name, target_date) == "succeeded":
        continue
    if not self._interval_due(defn, target_date, moment):
        continue
```

问题：
1. `newsflash` 09:26 跑成功后被 `run_task` → `_state_mark` 标成 `succeeded`（scheduler.py:346）
3. 下个 tick（09:26:15）走到 line 334，**`_state_status == "succeeded"` 直接 `continue`**
4. `_interval_due` 还没轮到判断，task 就被永久跳过

`interval_seconds=60` 的设计意图本来是"成功后 60 秒内不再尝试"，**但早退条件不应该跳过具有 interval 的任务**。
当前 `_interval_due` 在 newsflash 这类任务上形同虚设 —— `_state_status` 先把它挡了。

### 影响
- `newsflash` 09:26–10:00 窗口内本应 ~34 次执行，实际只跑 1 次
- 整个上午前端 `/api/newsflash` 拿到的就是 09:26 那 20 条，再也不会更新

### 复现条件
任意 `interval_seconds > 0` 的 task 都中招。`DEFAULT_TASKS` 里**只有 `newsflash` 是这个配置**，所以表现上"只有 newsflash"。
但是如果未来加任何 `interval_seconds > 0` 的 task 都会立刻复现。

### 建议修复方向（仅供开发者参考）
- **方案 A**：把早退条件改成 `interval <= 0 and status == succeeded`，否则一律走 `_interval_due` 判定
- **方案 B**：`_interval_due` 把 `state_status` 也纳入考虑 —— 若任务从未 succeed 则 interval=true；succeed 过的任务按时间间隔
- **方案 C**：删除 `interval_seconds` 配置，全部任务窗口内"每 tick 都跑"（简单但产生大量调用）

### 测试覆盖
`backend/tests/test_scheduler.py` 里**没有覆盖"interval>0 + 成功后是否重跑"**的用例。
建议加一个测试：mock newsflash 第一次 succeeded，模拟 60s 后再调 `run_once`，断言 newsflash 被再次执行。

## Bug #2: `newsflash` 09:26 那次 `rows=20` 但 DB `news_flash` 表 0 行

### 现象
- `ingest_jobs` 表今天上午有 1 条 newsflash 记录：`status=succeeded, rows=20`
- `news_flash` 表实际行数：`SELECT count(*) WHERE ts >= '2026-09-21 09:00:00'` = **0**
- `news_flash` 表最新一行的时间戳：`2026-09-20 22:50:54`（昨天晚上的，不是今天）

### 已查的事实
- `NewsFlash` 模型无 partition（market.py:220 `__tablename__ = "news_flash"`），不是分区路由问题
- `_write_newsflash` (`tasks.py:111-115`) 调用 `repos.news_flash.upsert_many(rows)`
- `NewsFlashRepository.upsert_many` (`market.py:326-328`) 走 `bulk_upsert(NewsFlash, rows, _NEWS_CONFLICT, _NEWS_UPDATE)`
- `bulk_upsert` (`base.py:181-230`) 用 PostgreSQL `INSERT ... ON CONFLICT DO UPDATE`
- `NewsFlash` 表有 `UniqueConstraint("ts", "title", name="uq_news_flash_ts_title")` (`market.py:221`)
- 唯一索引正常

### 可能的根因（需进一步排查）
1. **`rows` 计数与实际入库数不一致**：`IngestResult.rows` 可能是上游契约解析数，不是实际 `bulk_upsert` 的行数（后者返回 `len(materialized)`）。如果上游 `data.messages` 是 `[]` 但 `_write_newsflash` 还返回 20，说明上层把"契约校验通过"的 20 个字段计成 rows 了
2. **`bulk_upsert` 静默异常**：base.py:181-230 在 `await self.session.execute(stmt)` 时如果 schema 不匹配（缺字段、类型不对）会抛 `IntegrityError` 或 `ProgrammingError`，**但当前没有 try/except**，会冒泡到 `run_task` 的 `result.status`。但 `ingest_jobs` 显示 `status=succeeded, rows=20`，所以应该没抛 —— 那就回到了可能 1
3. **`session.commit()` 没真正刷新到 PG**：`run_once` 里有 `await session.commit()`（scheduler.py:347），但 newsflash 任务完成后**可能事务边界与 ingest_jobs 的写入不一致**，需要看 `_state_mark` 与 writer 的 commit 顺序
4. **9:26 那天上游 `xuangutong` 返回 401/空数据**，`XuangutongProvider.fetch` 返回 `code != 20000` 但 pipeline 没正确归类为 failed，导致 ingest_jobs 记成 succeeded，但实际 rows 是 0（不是 20），且没写入 DB

### 影响
- 整个 `news_flash` 表今天的快讯数据全是空白
- 前端 `/api/newsflash` 走 PG 直查，返回空

### 排查建议
1. 找到 `IngestResult.rows` 的赋值位置（pipeline.py），看它是从哪一步取的数
2. 加一个埋点：把 `bulk_upsert` 的 `len(materialized)`、实际 `INSERT` 语句的 rowcount 都打到日志
3. 单独跑一次 `python -m app.ingest.scheduler --once intraday --task newsflash --trade-date 2026-09-21`，看能不能落库
4. 临时 patch：把 `bulk_upsert` 改成 `await session.execute(stmt); result = await session.execute(...); logger.info("upserted=%s", result.rowcount)`

## 修复记录（2026-09-21 下午）

### Bug #1 — 已修复 ✅

**修法**：采用报告中的**方案 A**（`app/ingest/scheduler.py`）。早退条件改为：
「已完成不重跑」仅约束**一次性任务**（`interval<=0`）；周期任务（`interval>0`）
不再被 `succeeded` 状态挡住，窗口内一律走 `_interval_due` 按间隔判定。

- 语义变化：周期任务在 worker 重启后下一 tick 即重新到期（`_last_attempt`
  为进程内状态）；行级安全由 `bulk_upsert` 幂等覆盖写保证。
- 回归测试：`tests/test_ingest.py::test_interval_task_reruns_after_success_within_window`
  （成功 → 30s 不跑 → 61s 重跑；一次性任务语义不变）与
  `::test_interval_task_survives_scheduler_restart`（重启后立即到期）。

### Bug #2 — 数据大概率没有丢，是**排查口径的时区误读**（已加观测）⚠️

代码路径核查结论：

1. `_write_newsflash` 与 `ingest_jobs.finish` 走**同一事务**（同一 `AsyncSession`），
   `run_once` 在任务完成后立即 `session.commit()`。调查员能看到
   `ingest_jobs` 里 `status=succeeded, rows=20` 的记录 → **事务已提交** →
   同事务里的 `news_flash` 写入必然也已持久化。
2. `ts` 列为 `timestamptz`；映射 `sec_to_datetime` 统一产出**上海时区
   aware datetime**（transforms.py `_SHANGHAI`），存储的是正确绝对时间。

因此「`rows=20` 但表里 0 行」最合理的解释是**调查时 psql 会话时区为 UTC**：

- `WHERE ts >= '2026-09-21 09:00:00'` 的裸字面量被按 UTC 解释 = **CST 17:00**，
  而 09:26 CST 的快讯存的绝对时间是 UTC 01:26，自然不匹配；
- 「最新一行 2026-09-20 22:50:54」按 UTC 显示 = **CST 09-21 06:50**（今早盘前），
  与「昨晚快讯」的直觉相悖但完全自洽。

**复核 SQL**（正确姿势，显式指定时区）：

```sql
SELECT ts, ts AT TIME ZONE 'Asia/Shanghai' AS ts_cst, title
FROM news_flash
ORDER BY ts DESC LIMIT 20;

SELECT count(*) FROM news_flash
WHERE ts >= '2026-09-21 09:00:00+08';
```

**已加观测**：`BaseRepository.bulk_upsert` 现在记录 DB 实际影响行数
（`bulk_upsert_rowcount` 日志：`submitted` vs `db_rowcount`）。今后
「任务 rows=N 但表里查不到」直接看 worker.log 即可分辨是
「写库失败 / 键全冲突覆盖 / 查询口径问题」三者中的哪一个。

**回归测试**：`tests/test_ingest.py::test_newsflash_rows_land_in_db_and_queryable` —
newsflash 任务 `succeeded rows=N` 后，经 `list_recent` 必可查到 N 行且按 ts 倒序。
